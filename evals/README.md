# 평가셋

필수 조건 4 — **최소 30건**. 개선 전후를 같은 셋으로 비교합니다.

실행용 원본은 [dataset.jsonl](./dataset.jsonl)이며, 팀 검토용 요약표는
[evaluation-set.md](./evaluation-set.md)에서 확인합니다. `dataset.jsonl`의 각 줄은
독립 JSON이므로 줄바꿈·정렬을 바꾸지 않습니다.

## 기준 PRD

이 평가셋은 PRD의 사용자 흐름과 팀이 관리하는 정적 TERM_CARD 저장소 계약을 함께
검증한다. 특히 아래 인수 조건을 검증한다.

- 현재 런타임 허용 `term_id`와 역할만 선택하고, 선택 근거는 팀이 검수한
  `source_type=team_card` 카드에서만 가져온다.
- 선택 역할마다 카드의 `query_fragments`만으로 검색하고, 최대 8개의 Pin URL을
  Pinterest 공식 `pinit.js` `embedPin`으로 표시한다. Pin 이미지·썸네일·메타데이터는
  저장하지 않고 URL만 저장한다.
- 결과 0건·삭제 Pin·검색 오류·Cloud Run 작업 중단을 구분하고 다음 행동 또는 재시도를
  안내한다.
- 후속 chat에서는 지정한 역할만 다시 검색하고, 남겨 둔 Pin URL은 유지한다.

## JSONL 필드

| 필드 | 용도 |
| --- | --- |
| `category` | `normal` · `boundary` · `failure_inducing` · `prd_flow` |
| `prd_ac` | 원본 PRD의 Acceptance Criteria 번호 |
| `runtime_fixture` | 구현 후 테스트 환경이 주입할 LLM·Pinterest·정적 TERM_CARD 저장소·Cloud Run 상태 |
| `expected` | 상태·선택 용어·검색/Pin 결과·팀 카드 검수 정보·세션 보존의 기대값 |
| `judge` | 규칙 기반 검사를 먼저 하고, 필요할 때 설명 품질 평가를 추가한다는 뜻 |

`runtime_fixture`는 실제 외부 서비스를 조작한다는 뜻이 아니다. 테스트 double 또는
모의 응답으로 재현할 조건이며, 실제 배포 환경의 Pinterest 데이터·사용자 Pin을 기록하지 않는다.

## 측정 축과 판정

| 축 | 판정 | 점수 |
| --- | --- | --- |
| 계약·선택 정확성 | 활성 `term_id`, 역할, 금지 용어, 상태, 재시도, 검색 역할을 규칙 기반 검사 | 통과/실패 |
| 레퍼런스 흐름 정확성 | `query_fragments` 전용 검색, 역할별 최대 8개 URL, Pin 상태·세션 보존·팀 카드 검수 정보를 규칙 기반 검사 | 통과/실패 |
| 초보자 안내 품질 | 쉬운 설명·선택 근거·관찰 지점·혼동 안내·추가 질문의 충실도를 0~2점으로 평가 | 0/1/2 |

세 번째 축의 judge는 생성 모델과 다른 모델 또는 사람 검토자로 운영한다. judge는 응답 속도나
길이를 높게 평가하지 않고, 응답 안의 근거를 먼저 찾아 점수와 이유를 함께 남긴다. 실제 모델과
judge는 구현 후 Langfuse Dataset 실행 기록과 `EVAL_REPORT.md`에 명시한다.

## 구성

| 종류 | 왜 필요한가 |
|---|---|
| 정상 케이스 | 기본 동작 확인 |
| 경계 케이스 | 애매한 입력에서 어떻게 되는지 |
| 실패 유도 | 유해·부적절 입력, 스키마를 깨는 입력 |
| PRD 흐름 | Pin 미리보기·0건·삭제·오류·세션·출처·Cloud Run 실패를 확인 |

**잘 되는 것만 모으면 평가가 아니라 자랑입니다.** 실패 사례를 반드시 넣으세요.

## 판정 방식

정확 일치 · 스키마 통과 여부 · 규칙 기반 채점 · LLM-as-judge 모두 가능합니다.
다만 **어떤 방식이고 그 방식의 한계가 무엇인지** 리포트에 적어야 합니다.

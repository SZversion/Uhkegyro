# Illustration Reference User Experience Map

이 문서는 캐주얼 캐릭터 일러스트 레퍼런스 Agent가 다루는 사용자, 작업 흐름, 페인 포인트와 해결 경계를 한곳에 모은다. 앞부분은 최신 `docs/PRD.md`의 목표 사용자 경험을, 보관 절은 프로젝트의 도메인 경험과 경쟁 서비스 시작 흐름 관찰을 정리한 **MVP 가설**을 담는다. 어느 쪽도 사용자 인터뷰나 사용성 테스트 결과로 해석하지 않는다.

따라서 이 문서에서 `확인`은 도메인 경험 또는 공개 서비스 관찰로 확인된 범위만 뜻한다. `가설`은 목표 사용자를 대상으로 아직 검증하지 않은 제품 판단이고, `운영 위험`은 사용자 불편일 수 있으나 사용자 조사로 우선순위가 증명되지 않은 기술·권리 경계다.

## 현재 PRD 기준 사용자 경험

> 이 절의 흐름·상태·출처 경계가 이 문서의 현재 기준이다. 아래 `추가 도메인 근거와 상세 검증 계획`은 같은 경계를 따르며, 페르소나 가설과 경쟁 서비스 관찰을 보완한다.

### 사용자와 목표

| 항목 | 현재 기준 | 근거 상태 |
| --- | --- | --- |
| 핵심 사용자 | 캐주얼 캐릭터 일러스트를 시작했고 체형, 포즈, 시점, 원근, 배치의 전문 용어가 낯선 사람 | 도메인 프로필과 도메인 경험에 기반한 가설 |
| 시작점 | 1~500자 안에서 “한쪽 다리에 힘을 준 자세”, “아래에서 올려다보는 장면”처럼 일상어로 설명함 | 제품 입력 계약 |
| 목표 | 한 장의 정답 이미지를 받는 것이 아니라, 필요한 조건을 역할별로 나누고 여러 레퍼런스를 조합해 러프를 시작함 | PRD 목표 |
| 현재 제공 상태 | 공개 API는 `GET /health`뿐이며, chat·LLM·Pin 검색 provider·세션 저장·UI 미리보기는 아직 제공하지 않음 | 현재 구현 상태 |
| 이용자 제약과 세션 데이터 | Pin 이미지·썸네일·메타데이터는 저장하지 않고 Pin URL만 저장한다. chat·검색 이력은 1개월 뒤 삭제되며, 서버가 발급한 HttpOnly 쿠키 토큰으로 세션을 식별한다. 외부 원본의 저작권·출처·적합성은 사용자가 직접 확인한다. | PRD 범위·보안 정책 |

### 목표 사용자 파이프라인

```text
하나의 chat 세션에서 장면을 일상어로 설명
  → 단서가 부족하거나 충돌하면 한 가지 쉬운 질문에 답하고, 계속 해결되지 않으면 휴먼 피드백 필요 상태를 확인함
  → 활성 TERM_CARD 기반의 역할별 용어·뜻·확인 지점·혼동 안내를 읽음
  → 역할별 기본 최대 8개 Pin 미리보기를 `pinit.js`로 보거나, 결과 없음·삭제·검색 오류 상태와 재시도 안내를 확인함
  → 남길 Pin은 유지하고 필요한 역할만 다시 찾음
  → 원 출처 레퍼런스를 조합해 러프를 시작함
```

| 단계 | 사용자의 일 | 핵심 불편 | 목표 제품 반응 | 하지 않는 일 |
| --- | --- | --- | --- | --- |
| 1. 의도 설명 | 인물·자세·화면 느낌을 chat에 적음 | 전문 용어를 모르고 여러 조건이 한 문장에 섞임 | 실제 단서와 부족한 단서를 분리 | 입력에 없는 신체·포즈를 사실처럼 생성 |
| 2. 질문 또는 역할 분리 | 부족한 축을 답하거나 body·pose·view·perspective·layout을 구분 | 인물 시점·배경 원근·포즈를 혼동 | 부족하면 용어·링크를 추측하지 않고 한 질문; 계속 해결되지 않으면 `pending_human_review`로 표시 | 모든 역할을 억지로 채움 |
| 3. 카드 확인 | 용어, 쉬운 뜻, 관찰 기준, 혼동 안내를 읽음 | 모호한 표현을 확정 용어로 오해할 수 있음 | `runtime_eligible=true` 및 `mvp_status=active_in_current_contract`인 현재 활성 카드와 `confidence_gate`·`requires_all_of`·`requires_any_of` 조건만 사용 | 후보·비활성 카드, `detail`·`intent`·`style` 역할, 새 term ID 노출 |
| 4. 카드 검수 상태 확인 | 팀이 관리하는 카드의 검수 상태와 용어 설명을 봄 | 카드를 이미지 추천 또는 절대 정답으로 오해할 수 있음 | 저장된 용어·설명·검수 상태를 표시 | 외부 어휘 동적 조회, 이미지 카탈로그·RAG 사용 |
| 5. 역할별 탐색 | Pin 미리보기 또는 외부 탐색 안내를 확인 | 결과 0건, 삭제 Pin, 검색 오류가 다음 행동을 막음 | provider 확정 뒤 역할별 기본 최대 8개(설정 변경 가능) URL과 `no_results`·`deleted`·`search_error` 상태·재시도 안내를 구분하고, 같은 Pin이 여러 역할에 나오면 역할별로 중복 표시 | 이미지·썸네일·메타데이터 저장, 스크래핑, 품질 보증 |
| 6. 후속 요청과 러프 | 남길 결과를 유지하고 한 역할만 다시 찾은 뒤 러프 시작 | 한 이미지에 모든 조건을 찾으려 함 | 세션의 대화·보존 Pin·역할별 결과를 누적하되, chat·검색 이력과 Pin URL은 1개월 뒤 삭제 | 완성 그림·정답 구도·정답 이미지 판정 |

Pinterest 비즈니스 계정·API와 provider 계약은 아직 미정이다. 따라서 실제 provider가 확정되기 전에는 Pin 결과나 미리보기가 이미 제공되는 것처럼 말하지 않는다.

### 우선 검증할 가설

| 구분 | 가설 또는 위험 | 확인할 신호 |
| --- | --- | --- |
| P1 | 역할별 용어·검색 조각이 원문 전체 검색보다 첫 탐색을 쉽게 시작하게 한다 | 첫 검색어, 검색어 재작성 횟수, 막힌 지점 |
| P2 | `view`와 `perspective`를 분리한 설명이 축 혼동을 줄인다 | 역할 분리 전후 설명, 혼동 사례 |
| P3 | 낮은 확신도나 조건 미충족 시 추가 질문, 그 뒤 `pending_human_review`를 보이면 확정 용어로 오해하는 일을 줄인다 | 제안·휴먼 피드백 필요 상태를 사용자가 어떻게 이해하는지 |
| R1 | provider 미확정·0건·삭제·검색 오류·Cloud Run 작업 실패의 안내가 다음 행동을 분명히 해야 한다 | 상태별 재시도·역할 변경·외부 탐색 행동 |
| R2 | 팀 카드의 용어·검수 상태를 이미지 추천·저작권 보증으로 오해하지 않아야 한다 | 카드의 책임 범위에 대한 사후 설명 |

### 사용자 검증 질문

1. 역할별로 나눈 결과가 원문 전체 검색보다 실제로 더 쉽게 시작되는가?
2. `view`와 `perspective`를 분리한 설명이 혼동을 줄이는가?
3. 추가 질문이 가장 적은 재작성으로 이어지는 쉬운 말은 무엇인가?
4. 팀 카드의 용어·검수 상태를 이미지 추천이나 정답 판정으로 오해하지 않는가?
5. Pin 결과 0건·삭제·검색 오류·작업 실패 안내와 재시도 방법이 다음 행동을 분명하게 하는가?
6. 같은 Pin이 역할별로 중복 표시되는 이유를 이해하는가?
7. 후속 요청에서 남길 Pin을 유지하고 한 역할만 다시 찾는 방식을 이해하는가?
8. chat·검색 이력·Pin URL의 1개월 보관과 쿠키 기반 세션 식별을 이해하는가?

### 3. 사용자 파이프라인

#### 3-1. 사용자가 경험하는 여정

```text
그리고 싶은 장면을 일상어로 설명
  → 활성 카드의 역할별 용어 제안과 근거·한계를 읽음
  → 필요한 역할의 Pin 결과 또는 외부 탐색 안내를 확인함
  → 사용자가 원 출처에서 레퍼런스를 골라 조합하고 러프를 시작
```

| 단계 | 사용자의 일 | 페인 포인트 | 서비스의 역할 | 서비스가 하지 않는 일 |
| --- | --- | --- | --- | --- |
| 1. 의도 설명 | 그리고 싶은 인물·자세·화면 느낌을 일상어로 말함 | 전문 용어를 모르고, 한 문장에 여러 조건이 섞임 | 입력에서 확인된 단서와 모르는 단서를 분리 | 입력에 없는 신체·포즈를 사실처럼 생성 |
| 2. 조건 분리 | 체형, 포즈, 시점, 원근, 배치가 무엇인지 파악 | `low angle`과 `foreshortening`, 인물 방향과 배경 원근을 혼동 | 부족하면 질문하고, 확인된 역할만 순서를 유지해 제안 | 모든 역할을 억지로 채움 |
| 3. 용어 확인 | 활성 카드의 용어·근거·확인 지점을 읽음 | 모호한 표현을 하나의 전문 용어로 단정하기 어려움 | 활성 term ID와 confidence·requires 조건만 구조화 | 후보·비활성 카드나 새 term ID를 자동 생성 |
| 4. 카드 검수 상태 확인 | 팀이 관리하는 카드의 용어·검수 상태를 확인 | 카드를 이미지 추천이나 절대 정답으로 오해할 수 있음 | 저장된 용어·설명·검수 상태를 표시 | 외부 어휘 동적 조회, 이미지 카탈로그·RAG 사용 |
| 5. 외부 탐색 | 역할별 Pinterest 결과 또는 외부 탐색 안내를 확인 | 원문 전체 검색은 결과가 없거나 지나치게 넓고, 결과가 0건·삭제·오류일 수 있음 | 검증된 정적 검색 조각과 역할별 최대 8개 URL만 사용하고 상태·재시도 안내를 구분 | Pinterest 결과를 스크래핑·저장하거나 품질 보증 |
| 6. 후속 요청과 러프 | 여러 레퍼런스를 조합해 그림을 시작하고 필요한 역할만 다시 찾음 | 한 이미지에서 모든 조건을 찾으려다 관찰 기준을 놓침 | 보존 Pin과 역할별 결과를 세션에 누적하고 관찰 기준을 제공 | 완성 그림·정답 구도·정답 이미지를 판정 |

#### 3-2. 서비스를 구현할 때의 내부 처리

```text
사용자 일상어 입력
  → LLM이 허용 term ID 후보를 구조화
  → 결정론 코드가 활성 카드·역할·confidence·requires 조건을 검증
  → 카드 JSON에 기록된 팀 카드 용어·검수 상태를 조립
  → 정적 검색 조각으로 검색 입력 또는 외부 링크 생성
  → provider 계약 확정 후 UI가 역할별 Pin·근거·한계·출처·재시도 안내를 표시
```

이 처리 흐름은 사용자 여정이 아니라 구현 책임 분리를 설명하기 위한 것이다. 실제 API·오류 계약은 기능 Spec과 설계 문서를 따른다.

| 사용자 가설 P1 | 일상어를 검색어로 바꾸기 어렵다 | 도메인 경험과 Pinterest 원문 검색 관찰에 근거. 목표 사용자의 빈도·심각도는 미측정 | term ID, 쉬운 뜻, 역할별 검색 조각 제공 | 첫 검색어, 검색어 재작성 횟수, 막힌 지점 |
| 사용자 가설 P2 | 포즈·시점·원근·배치를 한 개념으로 섞는다 | 도메인 경험과 용어 혼동 사례에 근거. 목표 사용자의 이해도는 미측정 | 역할 분리와 축 검증 | 역할 분리 전후 설명, 역할 분리 사람 평가 |
| 사용자 가설 P3 | 모호한 표현을 확정 용어로 오해할 수 있다 | 제품 설계 가설 | confidence·requires 조건, 추가 질문, `pending_human_review` | 제안의 확정 여부와 휴먼 피드백 필요 상태를 어떻게 해석하는지 |
| 운영 위험 R1 | Pin 검색 provider의 0건·삭제·오류 또는 작업 실패가 다음 행동을 멈출 수 있다 | 외부 연동·비동기 작업 위험. 사용자 빈도는 미측정 | 상태·재시도 안내와 역할별 결과 누적 | 장애 주입 시 다음 행동과 재시도 이해 여부 |
| 운영·범위 위험 R2 | 외부 이미지의 출처·적합성을 서비스가 보증한다고 오해할 수 있다 | 저작권·책임 경계 | 외부 링크와 원 출처 확인 안내 | 범위 오해 관련 사용자 피드백 |

현재 P1·P2가 먼저 검증할 사용자 가설이고, P3은 이해도 가설, R1·R2는 제품 안전성·운영 경계다. 위 신호는 아직 측정 결과가 아니라, 이후 평가셋·사용성 검토에서 확인할 후보 지표다.

### 5. 제품 원칙과 경계

- **번역을 돕고, 그림을 대신 만들지 않는다.** 결과의 핵심은 이미지가 아니라 용어·근거·탐색 계획이다.
- **확인된 역할만 제안한다.** 체형 단서가 없으면 체형을 만들지 않고, 불확실하면 질문하거나 limitation을 표시한다.
- **카드 데이터는 팀이 관리한다.** TERM_CARD는 팀이 검수한 정적 용어·설명·선택 조건의 단일 원본이고, Pinterest는 사용자가 직접 확인할 외부 탐색 대상이다.
- **상태를 숨기지 않는다.** 단서 부족, Pin 0건·삭제·검색 오류·작업 실패를 구분하고 다음 행동·재시도 안내를 표시한다.
- **판정과 학습 데이터화를 하지 않는다.** 사용자 원문과 이미지를 RAG·모델 학습·자동 term 카드 생성에 사용하지 않는다.

### 6. 사용자 검증 계획

| 항목 | 초기 계획 |
| --- | --- |
| 참여자 | 캐주얼 캐릭터를 그리기 시작했고 드로잉 전문 용어가 낯선 사람 3~5명. 팀원·도메인 담당자만으로 사용자 결론을 내리지 않는다. |
| 과제 | 일상어로 캐릭터 장면 하나를 설명하고, 현재 사용 방식 또는 프로토타입으로 레퍼런스 탐색을 시작하게 한다. |
| 관찰 | 첫 검색어, 역할 분리 시 혼동, 검색어 재작성, 카드 출처·한계 이해, Pin 상태별 다음 행동, 보존 Pin·부분 재검색 이해를 기록한다. |
| 사후 질문 | 무엇이 가장 막혔는지, 제안이 확정인지 후보인지 어떻게 이해했는지, 링크가 다음 행동에 도움이 됐는지 묻는다. |
| 개인정보 경계 | 동의 없는 원문 이미지·식별자·녹음은 저장하지 않는다. 결과는 익명 요약과 필요한 최소 인용으로 기록한다. |
| 판단 | 이 문서의 각 가설을 유지·수정·폐기로 표시한다. 참여자 수, 과제, 관찰일, 상반된 사례를 함께 남긴다. |

처음 검증에서는 기준선과 목표값을 미리 주장하지 않는다. 관찰된 첫 시도 결과를 기준선으로 기록한 뒤, 이후 같은 과제로 비교 가능한 목표를 팀이 합의한다.
